# Session 2026-09-02 — blockwise activation quantization for the conv path

Everything in this session concerns one question: put the activation scale on **sub-tensor blocks
along C** instead of per-tensor, for the int8/int4 conv. Six new doc directories; read them in
this order.

| # | doc | one line |
|---|---|---|
| 1 | `delta_dynamic_2026-09-02` | `MODIFF_DELTA_MODE=dynamic` is 2.8% slower and no better. Calibrated static ties it. |
| 2 | `act_budget_2026-09-02` | first error budget. **Partly superseded — its floor is 3x too high**; see the header. |
| 3 | `wa_budget_2026-09-02` | the corrected budget, W8A8 **and** W4A4, plus weight granularity. **The decision document.** |
| 4 | `conv_blockk_e2e_2026-09-02` | wiring the int8 blockwise conv into the model; final W8A8 E2E numbers. |
| 5 | `conv_shape_sweep_2026-09-02` | fp16 vs int8 vs blockwise across (B, N, H, W, C) and the 20 real shapes. |
| 6 | `conv_int4_blockk_2026-09-02` | the int4 kernel + `TUNE_FINDINGS.md`, the 16-config tile x B sweep. |

## The three results that matter

**Blockwise belongs at 4 bits, not 8.** `wa_budget`: the activation-granularity term is
per-tensor 0.0382 vs blockwise 0.0097 at 8 bits (the latter is at the 0.0113 floor, i.e. the term
stops existing) but **0.5181 vs 0.0415 at 4 bits — 12.5x**. Full stack W4A4 goes 0.5051 -> 0.2034.

**The blockwise tax is multiplicative, so it only pays where the baseline is fast.** Same
mechanism, same ~1.5x relative cost at both precisions, opposite outcome:
W8A8 1.76x baseline / 1.72x tax = **1.02x, nothing left**; W4A4 3.12x / 1.84x = **1.70x**.

**Do not make the weights blockwise.** Measured 1.0x at 8 bits and only 1.29x at 4 bits, against
permanently moving the weight scale off the free axis (per-output-channel factors out of the
reduction and is applied once in the epilogue). DeepSeek-V3's 128x128 weight blocks are an FP8
dynamic-range constraint, not a granularity insight, and per-output-channel here is already
*finer* than their blocks.

## Goal not met: 80% of shipped conv speed

`conv_int4_blockk_2026-09-02/TUNE_FINDINGS.md` has the full 16-config benchmark for both
precisions. Best: **W8A8 65.2%**, **W4A4 65.1%** of shipped. The blockwise *tax* target was met
(1.03-1.14x with `CTA_K*EPB == BLK`, which removes the cross-tile accumulator carry — the earlier
"large B is slower" result was entirely that carry, not ALU). The binding constraint moved to the
tile, and it is a shared-memory trade-off that no parameter breaks: removing the carry needs
K=128 bytes, 2 CTA/SM then forces `CTA_M+CTA_N <= 192`, and the smaller tile is what costs
efficiency. Even the impossible best-tile+lowest-tax combination is 81.7% (int8) and 74.7%
(int4).

## Open items, in the order I would take them

1. **The MoDiff arm of the fused int8 blockwise path is wrong** (relL2 ~0.49 vs 0.0641 two-pass).
   Kernel recursion verified correct in isolation; path mixing eliminated. The defect is in the
   `o_hat` wiring in `blockk_gn_fused`. Only the BASELINE E2E numbers are valid.
2. **int4 is not wired into the model at all.** `int4_optimized.py` has no `MODIFF_CONV_BLOCKK`
   path and no sim harness. Also needs a fused GN->int4-blockwise-quantize kernel (the int8 one
   recovered ~18 ms/step) and the shipped int4 path's zero-point handling reconciled — this
   kernel is symmetric.
3. **Coverage.** int8 blockk needs `C % 64 == 0` (all 70 layers pass). int4 needs
   `C % 128 == 0` — 58/70 layers, but that is **29% of conv time** missing, not the 2.8% of
   weight-MACs an earlier note claimed. A 32-byte-row variant (reworked loaders + 1-bit swizzle)
   would close it.
4. **`act_block32_quality.py`** (in `act_blockwise_2026-09-01`) is a dead script — final-latent
   relL2 cannot resolve granularity. Rewrite against per-layer error or FID.
5. **I-MoDiff E2E relL2 3.23** — unrelated, still unexplained, kernel invariants pass.
6. Unresolved harness discrepancy: the production W8A8 path reads 81.65 ms/step in the
   `ahat_blockwise` env block and 72.20 in `pipeline_profile_2026-08-31`. fp16 agrees across both
   (101.92 vs 102.23), so it is in the int8 path only. Any projection that scales the 37.81 ms
   conv bucket inherits this.

## Rebuilding after the server migration

Environment this was built and measured on: **A40 (sm_86)**, CUDA **12.4** (`nvcc` 12.4.131),
torch **2.4.1+cu124**, Python 3.11, CUTLASS at `/workspace/cutlass`.

```bash
source /workspace/MoDiff/setup_cuda_env.sh     # CUDA_HOME + the nvjitlink LD_LIBRARY_PATH order
```

Do **not** run `python setup.py build_ext --inplace` for a change confined to these kernels — it
recompiles every CUTLASS conv (~32 min). Use the incremental script, passing any extra `.cu`:

```bash
bash docs/ahat_blockwise_2026-09-01/scripts/rebuild_ahat.sh csrc/modiff/conv/conv2d_int8_blockk.cu csrc/modiff/conv/conv2d_int4_blockk.cu csrc/modiff/conv/conv2d_blockk_tune.cu
```

Two build gotchas that cost time here: **`pybind.cpp` must be recompiled whenever a bound
signature changes** (a shared-object link does not error on the stale symbol, it fails at call
time), and **CUDA 12.4 does not do FFMA interleaving automatically** — NVCC 12.9+ does, which is
worth knowing if the new server has a newer toolkit, since the flush is dense FFMA and DeepGEMM
reports 10%+ from that transformation.

`modiff_cutlass.cpython-311-x86_64-linux-gnu.so` is gitignored, so the extension must be rebuilt
on the new machine before any of the scripts here will run.
